# Post-mortem: Mast unusable after restart (releases 90–94, fixed in 95)

Date: 2026-11-16. Author: Mast Dev coordinator.

## Impact

For most of 2026-11-16 Mast was too slow to use: typed text appeared late, the sidebar lagged, and every restart
started with minutes of 200–380% CPU. Mikey could not work in it. It took five releases (91–95) to clear. One of them
(90) also crashed Mast (variable-bound `clamp`, fixed in 92).

## What was slow, release by release

| Release | Cause found | Fix |
| --- | --- | --- |
| 93 | Diff-sync watch-budget walks re-walked every checkout after each restart and pinned ~8 cores | Bound and cache the walks |
| 94 | The menu-bar status item was rebuilt every ~900 ms (~40% of the main thread) | Rebuild only on change |
| 95 | `git` spawn storm from pull-request (change-request) watches, every spawn a full `fork()`; sidebar PR rows scanning the whole outline every frame | See below |

Release 95 profile 2 minutes after launch: 3–56% CPU (spiky, settling); at 36 minutes 3–17% CPU, 1.1 GB footprint. Release 94 at the same point: 200–380%.

## Root causes of the release-95 issue

1. **Per-call fan-out with no cache.** `WatchCheckoutChangeRequest` resolves the chat's folder with
   `change_request_root`. For a folder that isn't a chat cwd it walked every git Space and ran `Repos::refs` on each,
   about 5 `git` processes per Space per call (`git branch -a`, `symbolic-ref`, 2 × `branch --show-current`,
   `worktree list`), when it only needed the worktree list. It also re-ran the walk on every chats/spaces change in its
   250 ms window. Introduced with the composer's workspace mentions (07ba53dca, 2026-08-03) and reused by the
   change-request stream (3adc1551e, 2026-08-15).
2. **Fixed-interval retry forever.** When that lookup failed ("not a known checkout"), the UI retried every 2 s with no
   backoff (bdc8363d3, 2026-08-15). A deleted worktree is a permanent failure, so each stale chat became a loop of
   ~5 × Spaces `git` spawns every 2 s. Mikey was deleting ~80 old worktrees that afternoon. Likely, not measured: the
   retry logs at debug level, so the count of failing watches is unknown.
3. **Every `git` spawn forked the whole process.** Since fe3c3bb16 (2026-10-19, Git LFS fix) `git_command()` set `PATH`
   on the child and ran the bare name `git`. Rust's std then skips `posix_spawn` and uses `fork`+`exec`, which copies the
   page tables of a 2.7 GB process and serialises spawns on a process-wide lock. Samples showed `__fork` and
   `__ulock_wait2` under every `Repos::git`. This made causes 1 and 2 roughly an order of magnitude more expensive and
   hid in the profile for four weeks.
4. **No concurrency bound on child processes.** Watches, discovery and RPC handlers spawned `git` freely, so bursts
   ran dozens at once.
5. **Per-row, per-frame whole-snapshot scans in the sidebar.** Each PR row called `review_chats::for_pr`, which looped
   over every outline item and re-derived its PR links (`afeae87ab`, `0b779dfc5`, 2026-10-23). ~37% of the main thread
   on 94.

## Why it shipped and why it took five releases

- **Tests run at toy scale.** Fixtures have one or two repos and a handful of chats. Mikey's setup had ~110 worktrees,
  dozens of chats and hundreds of outline items. Every cause above is O(Spaces), O(worktrees) or O(items × rows), so it
  was invisible in tests.
- **No budget on background work.** Nothing asserts how many processes, walks or redraws an idle Mast may do. A
  spawn counter existed (`mast_harness::git_spawn_count`) but no test or log used it.
- **No perf check in the release flow.** Mikey was the detector. Each release fixed the top item in one profile, then
  waited for him to restart and report.
- **Slowness compounded.** Up to 4 concurrent Rust builds (load 44 on 18 cores) made Mast lag on their own and muddied
  which fix helped.
- **Debug-level logging hid the loop.** The retry message was `debug`, so the log showed nothing.

## What we changed (release 95)

- `change_request_root` canonicalizes once and checks a per-Space cached worktree set (one `git worktree list`,
  60 s TTL, refreshed at most every 3 s on a miss, single-flight). Unresolvable paths never reach git.
- UI change-request watches back off 2 s → 5 min on `BadParams`, and wake early when the watch set changes.
- Engine-wide gate: at most 4 concurrent local `git` children (network ops exempt in the follow-up).
- `git_command()` runs git by absolute path, so std uses `posix_spawn`.
- Sidebar: PR links and review assignments are indexed once per snapshot.

## Prevention

| # | Action | Kind |
| --- | --- | --- |
| P1 | **Idle-budget test** in the release suite: an engine with ~100 worktrees across several Spaces, ~50 chats (some with deleted cwds) and active change-request watches, run for a simulated few minutes; assert total `git` spawns stay under a budget and no watch retries faster than its backoff. Same for an outline with ~500 items and ~50 PR rows: index builds once per snapshot | test |
| P2 | **Runtime spawn and busy alarms:** log a `warn` once a minute when `git` spawns exceed a threshold (with a per-caller tag), and land the freeze watchdog (17c9d278) so main-thread stalls leave a stack | runtime |
| P3 | **One way to spawn:** clippy `disallowed-methods` for `std::process::Command::new` / `tokio::process::Command::new` outside `mast_harness`; harness helpers always resolve an absolute program path and take the gate | lint |
| P4 | **One way to retry:** a shared backoff helper; reviewers reject fixed-interval retry loops and treat "not found / bad params" as non-transient | code rule |
| P5 | **Fan-out and render rules for reviews:** any per-Space, per-worktree or per-chat loop that runs git or I/O must be cached and bounded; render paths must not scan whole snapshots or chat lists per row, precompute per revision | review checklist |
| P6 | **Perf check in every release:** after Mikey restarts, the coordinator runs `scripts/perf-sample.py` about 2 minutes after launch and records CPU, physical footprint and top frames in HANDOFF. Steady CPU above ~25% or footprint growing more than 1 GB in 15 minutes blocks further feature releases | process |
| P7 | **Builds stay ≤ 2** (already a HANDOFF rule) | process |

## Still open

- Release 94's "8 GB" was RSS, which counts mapped GPU memory. On 95 RSS read 6.4 GB while the physical footprint
  was 1.1 GB (peak 1.8 GB). Not a leak; the gate measures footprint.
- `pr_ticket_cache` (`gh pr view` / search) and `diff_sync::read_head` lead the remaining startup profile.
- Spinner ticks still re-render the sidebar (2694931e).
